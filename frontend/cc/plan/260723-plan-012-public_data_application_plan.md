## 1. 전제 — 현 프로젝트 상태

- 메인(`features/main`)은 인기 플랜/장소 4종 API가 실연동 완료 (`main.api.ts` → `/api/plan|place/popular*`)
- 검색(`features/search`)은 최근 검색어 CRUD 실연동, 장소 검색은 백엔드 기반
- 코스 생성(`features/course-creation`)은 감정 설문 + 장소 추천 API(`POST /api/place/recommend`) 연동 완료
- v6 정합화 작업(plan-011)이 선행 중 → 공공데이터 작업은 **plan-011과 파일 충돌이 없는 신규 레이어 위주로 병행 가능**
- 비활성 기능(피드, 매거진)은 적용 범위 제외

## 2. 활용 분류 → 적용 계획

### 분류 A. 메인 페이지 콘텐츠 후보 (API 1, 2)

**"이달의 인기 여행지" 지역 카드 섹션**

- 대상: `features/main` — 기존 "전국 인기 플랜/장소" 섹션 패턴 그대로 재사용해 지역 카드 3~5개 섹션 추가
- 데이터: API 1 `tarSvcDemIxCd=11`(전체 지수)로 지역 랭킹, API 2(체류·소비 강도)를 가중치/보조 지표로
- BFF: `GET /api/public-data/popular-regions` 신설 — 월 단위 데이터(`baseYm`)이므로 revalidate 24h 이상 장기 캐시
- 지역 카드 클릭 → 지역 리포트 페이지(`app/region/[code]/page.tsx` + 신규 `features/region-report`). 기존 `features/report`는 신고 도메인이므로 반드시 분리
- 리포트 내용: 수요 지수 요약 + 해당 지역 플랜 목록(기존 인기 플랜 API에 지역 필터 적용 가능 여부 백엔드 확인) → 플랜 상세로 연결

### 분류 B. 플랜 생성 시 장소 추천 (API 5, 7, 12) — AI 플랜 생성과 연계

> 플랜 생성에 AI API를 활용할 예정이므로, 공공데이터는 사용자에게 직접 노출하는 추천 소스이자 **AI에게 전달하는 후보 풀(grounding 데이터)** 두 역할을 겸한다. 상세 구조는 §6 참고.

**감정 설문 → 웰니스 장소 추천 (API 5, 최우선)**

- 대상: `features/course-creation`, `features/emotion-analysis`
- 감정 설문 결과 → 웰니스 `contentTypeId`/키워드 매핑 테이블 정의 (지치고 기운없음 → 온천·스파, 멍한 느낌 → 바다·자연)
- 이 매핑으로 조회한 웰니스 장소 목록을 **AI 플랜 생성의 후보 풀에 포함** — AI가 자유 생성한 장소명이 아니라 실존 장소(`contentId` 보유) 중에서만 고르게 하는 hallucination 방지 장치로 활용
- 사용자 직접 탐색 화면에서는 백엔드 추천(`POST /api/place/recommend`)과 **이중 소스**로 병치: 백엔드 추천 = 기본, 웰니스 = "힐링" 배지 카드
- 공공데이터 장소를 플랜에 담을 때는 카카오 `keywordSearch`(장소명+좌표 반경) 매칭 → 성공 시 카카오 장소로 저장, 실패 시 공공데이터 식별자만 저장하고 표시 시 재조회 (§5 저장 제약 참고)

**반려동물 동반 옵션 (API 7)**

- 설문에 "반려동물과 함께" 선택지 추가 → 추천 소스를 `KorPetTourService2`로 전환
- 동반 조건(`detailPetTour2`: 가능 견종, 준비물 등)은 장소 상세의 별도 섹션으로

**두루누비 걷기 코스 (API 12)**

- 코스 작성 시 "걷기 코스 통째로 추가" 옵션: 코스명·거리·난이도·소요시간 카드 제공
- `gpxpath`는 BFF에서 좌표 배열로 파싱 → 지도 Polyline 렌더 (지도 인프라(plan-009) 완료가 선행 조건)

### 분류 C. 장소 검색 (API 5, 7, 12)

- 대상: `features/search`
- 힐링 키워드 검색: API 5 `searchKeyword` 결과를 기존 검색 결과 리스트에 "웰니스" 탭/섹션으로 병치 (기존 백엔드 검색과 소스 구분 표시)
- "반려동물 동반 가능" 필터 토글 → 활성 시 API 7으로 라우팅
- 지역 탐색: API 5 `areaBasedList` + API 7 `ldongCode2`(시도·시군구 코드)로 지역 드롭다운
- 최근 검색어 로직은 기존 것 그대로 재사용 (공공데이터 검색어도 동일하게 `POST /api/recent` 기록)

### 분류 D. 필요한 장소 정보 뽑아서 활용 (API 16, 17)

- **이미지 fallback**: 이미지 없는 장소 카드에 API 16(관광사진) 키워드 매칭 이미지 사용. 관광 명소 위주라는 한계 → 매칭 실패 시 기존 placeholder 유지. `cpyrhtDivCd` 저작권 구분 확인 필수
- **생태 관광(API 17)**: totalCount 5 수준으로 데이터가 빈약 → 독립 기능이 아니라 웰니스 추천 결과에 "생태" 태그 장소로 소량 병합하는 수준으로만
- 구현 위치: BFF 정규화 레이어의 이미지 보강 단계 (feature 코드 수정 최소화)

## 3. 공통 아키텍처 (plan-010 방침 유지)

1. **BFF 경유**: 서비스 키 비노출을 위해 모든 공공 API는 `src/app/api/public-data/*` 경유. plan-011 Phase 4-1의 공통 프록시 유틸(`src/app/api/_lib/proxy.ts`)이 만들어지면 fetch/에러 처리 패턴 공유
2. **`Place` DTO 정규화**: 서비스별 상이한 필드(`contentId`/`contentid`, `firstimage`/`orgImage`)를 `src/shared/lib/types/publicData.ts`에서 공용 DTO로 통일, 좌표는 카카오 관례(`x/y`)로
3. **캐싱**: 월 단위 데이터(A) 장기 캐시, 위치기반(B, C)은 좌표 반올림 + 수 분 캐시
4. **FSD 준수**: 페이지 thin wrapper, 로직은 feature hooks, feature API 파일은 `{feature}.api.ts` 패턴

## 5. 데이터 저장 제약 — 식별자만 DB 저장 가능

공공데이터 원문(장소명, 주소, 이미지, 지수값 등)은 자체 DB에 영구 저장할 수 없고 **식별자만 저장 가능**하다는 제약을 전 영역에 적용한다.

> **공모전 사무국 공식 확인 (2026-07)**: "식별자만 DB 저장 + 실시간 TourAPI 호출로 표시" 구조는 정상 활용 형태로 심사 대상에 포함됨. 단, **개발 기간 내 OpenAPI 실제 호출 로그가 심사에서 검증되므로 호출 로그를 반드시 남길 것**. 상세: [260723-docs-005-공모전_공공데이터_저장규정_공식답변.md](../docs/260723-docs-005-공모전_공공데이터_저장규정_공식답변.md)

### 5.1 원칙

- **DB에 저장하는 것**: 공공데이터 식별자(`contentId` + 출처 API 구분값), 사용자가 생성한 데이터(플랜, 좌표, 사용자 입력 메모)
- **DB에 저장하지 않는 것**: 장소명·주소·이미지 URL·소개문 등 공공 API 원문, 수요 지수 등 원천/파생 통계값
- **표시 시점 재조회**: 식별자로 저장된 장소는 렌더 시점에 공공 API를 재호출해 표시. BFF의 단기 인메모리/HTTP 캐시(수 분~수 시간)는 "저장"이 아닌 전송 최적화로 간주하되, 영속 스토어(DB, 파일) 적재는 금지

### 5.2 영역별 영향

| 영역 | 영향 및 대응 |
| --- | --- |
| 플랜에 공공데이터 장소 담기 (분류 B) | 백엔드 플랜 스키마에 `publicDataRef`(출처 API + `contentId`) 필드 필요 — **백엔드 스키마 협의 필수**. 카카오 매칭 성공 시에는 카카오 장소로 저장되므로 제약 무관. 매칭 실패 시 "좌표-only 저장" 대신 "식별자 저장 + 표시 시 재조회"로 변경 |
| 플랜 상세/내 코스 표시 | 공공데이터 장소가 포함된 플랜은 상세 조회 시 BFF에서 `contentId`로 detail 재조회 후 병합 → 응답 지연 및 공공 API 장애 시 성능 저하. 장애 시 "장소 정보를 불러올 수 없음" placeholder 필수 |
| 메인 랭킹 (분류 A) | plan-010의 "스케줄러 사전 집계(지수값 DB 적재)" 옵션 **폐기**. BFF 단기 캐시(월 단위 데이터라 24h 캐시로 충분)로만 처리 |
| 이미지 fallback (분류 D) | 이미지 URL을 장소 레코드에 저장 불가 → 렌더 시점에 BFF가 키워드 매칭 후 URL을 응답에 병합(비영속). 비용 대비 효과 재평가 필요 — 우선순위 하향 |
| 두루누비 GPX (분류 B) | GPX 파싱 결과(경로 좌표 배열)도 원문 파생 데이터 → DB 저장 불가. 플랜에는 두루누비 코스 식별자만 저장, 경로는 표시 시 재조회·파싱 |
| 검색 (분류 C) | 검색 결과는 원래 비저장(휘발성)이므로 영향 없음. 최근 검색어는 사용자 입력이므로 저장 가능 |

### 5.3 삭제·변경 대응

- 공공 API에서 해당 `contentId`가 삭제/응답 실패하는 경우: 플랜 내 해당 장소를 "정보 만료" 상태로 표시하고 사용자에게 교체 유도. 플랜 자체는 유지

## 6. AI 플랜 생성과 공공데이터 연계

플랜 생성에 AI API를 활용하는 전제에서, 공공데이터는 AI의 **grounding 소스**로 쓴다. AI가 장소를 자유 생성(hallucination)하지 않도록 후보 풀을 공공데이터·카카오·백엔드 장소로 한정하는 구조가 핵심이다.

### 6.1 데이터 흐름

```
감정 설문 + 위치/조건
  → [후보 수집] 공공 API(5/7/12) + 백엔드 추천 장소를 후보 풀로 조회
  → [AI 호출] 후보 풀(장소명·유형·좌표·contentId 요약)을 컨텍스트로 전달,
              "이 목록 안에서만 골라 코스를 구성하라"고 제약
  → [응답 검증] AI가 반환한 장소를 contentId/placeId로 후보 풀과 대조,
              풀에 없는 장소는 폐기 또는 재요청
  → [플랜 확정] 식별자만 DB 저장 (§5 제약 그대로 적용)
```

### 6.2 설계 포인트

1. **AI 호출 위치**: 후보 수집(공공 API 다건 호출) + AI 호출 + 검증을 한 곳에서 처리해야 하므로, 백엔드(3845) 또는 BFF의 단일 오케스트레이션 엔드포인트로 구성. 클라이언트는 설문 결과만 보내고 완성된 플랜 초안을 받는 형태 (AI 키·공공 키 모두 비노출)
2. **후보 풀 요약 전달**: "식별자만 저장" 제약은 DB 영속화에만 적용되고 AI 전달 시점과는 무관 — 생성 시점에 공공 API를 실시간 호출해 받은 원문(이름·유형·주소 등)을 프롬프트에 사용할 수 있다 (일시적 처리이며, 매번 실호출하므로 호출 로그 요건에도 부합). 단, **기존 플랜을 AI로 수정·재생성할 때는 DB에 식별자만 있으므로 AI 호출 전에 `contentId`로 detail 재조회하여 원문을 복원하는 단계가 반드시 선행**되어야 한다. 프롬프트에는 원문 전체가 아니라 최소 필드(이름·유형·주소 요약·좌표·식별자)만 포함 — 토큰 비용 절감 + 원문 재배포 우려 축소. AI에 전달하는 것은 일시적 처리이므로 §5의 "저장" 제약과 충돌하지 않으나, AI 제공사의 데이터 학습 미사용 옵션 확인 필요
3. **저장 제약과의 정합**: AI가 구성한 플랜도 결국 장소 참조는 식별자(`publicDataRef` 또는 카카오 `placeId`)로만 저장. AI가 생성한 텍스트(코스 소개문, 추천 이유)는 자체 생성물이므로 저장 가능 — 단, 공공데이터 원문을 그대로 복사한 문장이 되지 않도록 프롬프트에서 "요약·재구성" 지시
4. **응답 시간 UX**: 후보 수집(공공 API 수 회) + AI 생성으로 플랜 생성이 수 초~수십 초 소요 가능 → `features/course-creation`에 생성 중 로딩/스트리밍 UI 필요. 실패 시 AI 없이 후보 풀 상위 장소로 구성하는 non-AI fallback 경로 유지 (현재의 `POST /api/place/recommend` 흐름이 그대로 fallback이 됨)
5. **두루누비(API 12)와의 결합**: 걷기 코스는 AI가 임의 분해하지 않고 "코스 통째로 추가" 단위로만 후보에 제공 (GPX 경로 무결성 유지)

### 6.3 트래픽 영향

AI 플랜 생성 1회당 공공 API 후보 수집 호출이 여러 건 발생 → §5로 늘어난 표시 시 재조회와 합산하면 호출량이 상당해짐. 후보 풀 조회는 좌표 반올림 + 조건 키 기반 단기 캐시를 반드시 적용하고, 일일 한도 초과 시 non-AI fallback으로 강등.

## 7. 미결 사항 (팀 논의)

1. 공공 API 호출 주체: 프론트 BFF 직접 vs 백엔드(3845) 프록시 — 키 관리·캐싱 위치
2. 각 API 일일 트래픽 한도 및 초과 시 fallback 정책 — **식별자-only 제약으로 표시 시 재조회가 늘어나 호출량이 증가하므로 한도 확인이 더 중요해짐**
3. 지역 리포트의 "해당 지역 플랜 목록" — 기존 플랜 API에 지역 필터 지원 여부
4. API 4, 16 이미지의 `cpyrhtDivCd` 타입별 사용 허용 범위
5. 랭킹 산출식(API 1 주지표 + API 2 가중치) 계산 위치 — 저장 제약(§5.2)에 따라 BFF 단기 캐시 방식으로 기울어짐, 백엔드 스케줄러 채택 시 지수값 적재 가능 여부 법무/약관 확인 필요
6. **플랜 스키마에 공공데이터 식별자 필드(`publicDataRef`) 추가** — 백엔드 협의 (§5.2, 분류 B의 선행 조건)
7. BFF 단기 캐시의 허용 범위 — 사무국 답변으로 "원문 통째 복사 후 API 호출 없이 서빙"만 금지임이 확인되어 단기 캐시는 허용 범위로 해석. 단, 상세 규정 문서는 한국관광콘텐츠랩 Q&A/고객센터에 별도 확인 필요. 또한 **실호출 로그가 심사 요건이므로 캐시 TTL은 실호출 내역이 충분히 남는 수준으로 설계** (docs-005 참고)
8. **AI 오케스트레이션 위치** — 백엔드(3845) vs 프론트 BFF: 후보 수집 + AI 호출 + 검증을 어디서 수행할지 (§6.2-1). AI API 키 관리 주체와 직결
9. **AI 제공사 약관 확인** — 프롬프트로 전달한 공공데이터가 모델 학습에 사용되지 않는 옵션(zero data retention 등) 여부 (§6.2-2)
10. AI 생성 실패/한도 초과 시 non-AI fallback 기준 및 사용자 안내 문구 (§6.2-4, §6.3)
