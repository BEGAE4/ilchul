## 0. 세 줄 요약

1. **플랜 생성 3단 파이프라인(추천 → 프리뷰 → 생성)의 요청 스키마는 FE 구현과 100% 일치**한다. 손댈 곳이 없다.
2. **깨져 있는 곳은 1단계 `POST /api/place/recommend` 응답 하나뿐**이다. 명세는 여전히 타입을 비워뒀고(`type: object`), 실제 백엔드는 `List<RecommendPlaceResponseDto>`(키워드별 그룹)를 반환하는데 FE는 평면 배열을 기대한다 → 추천 결과가 전량 폐기되고 목데이터가 노출된다. (ans-014 §3-2 버그, 여전히 미수정)
3. **명세에 `SurveyResultDto.transportTime`이 부활**했다. FE가 "서버에 없는 필드"라며 꺼둔 `TODO(transportTime)` 블록을 되살릴 수 있다.

### 1-1. 데이터가 흐르는 방식 (필드 단위)

```
설문(emotion/startTime/endTime/transport/location[, transportTime])
   → POST /api/place/recommend
   → 추천 장소 목록 (placeId 확보)
        ↓ 사용자가 선택 + 순서 지정
   → POST /api/plan-place/preview  { places: [{placeId, order}], departurePoint, tripStart/EndDate }
   → requiredTime, totalDistance, places[].duration, places[].stayTime  ← ★ 서버 계산값
        ↓ 이 값들을 그대로 다음 요청에 실어 보냄
   → POST /api/plan/create  { requiredTime, totalDistance, places: [{placeId, order, travelTime, stayTime}] }
   → { planId }
```

**핵심 제약: 2단계(프리뷰)를 건너뛰면 3단계(생성)에 넣을 `requiredTime`/`totalDistance`/`travelTime`/`stayTime`을 만들 수 없다.** 프리뷰는 선택이 아니라 생성의 선행 조건이다.

## 2. 명세 대비 FE 구현 차이

### 2-1. ✅ 일치 — 수정 불필요

`CreatePlanPreviewRequestDto`, `CreatePlanPreviewResponseDto`, `CreatePlanRequestDto`, `CreatePlanPlaceRequest`, `CreatePlanResponseDto`, `PlanPlacePreview`, `DeparturePointDto`, `UpdatePlanPlaceRequestDto`, `UpdatePlanPreviewResponseDto`, `UpdatePlanRequestDto`, `StampPlanPlaceResponseDto`, `PlanCopyRequestDto/ResponseDto` — 전부 `plan.types.ts`와 필드명·타입이 동일하다.

FE가 호출하는 22개 경로 전부가 명세에 존재한다. **삭제·이름 변경으로 인한 회귀는 없다.**

### 2-2. 🔴 P0 — 추천 응답 스키마 불일치 (실사용자 영향)

명세상 `POST /api/place/recommend`의 200 응답은 `{"type": "object"}` — 즉 **아무 정보가 없다.** 컨트롤러가 `ResponseEntity<?>`로 선언돼 springdoc이 타입을 추론하지 못한 결과다.

`backend/.../PlaceController.java:49` 실제 반환:

```java
List<RecommendPlaceResponseDto> result = ...   // { keyword, radiusM, places: List<SearchPlaceResponseDto> }
```

FE `mapRecommendedPlaces`(`CourseCreationFlow.tsx:45`)는 평면 장소 배열을 기대하므로, 그룹 객체에서 `placeId`/`placeName`을 찾지 못해 **모든 항목을 버리고** `RECOMMENDED_PLACES`(목데이터)로 폴백한다(`:367`).

> ans-014 §3-2에서 이미 지적된 버그이며 **2026-08-19 명세에서도 여전히 타입이 비어 있어 미수정 상태**로 판단된다.

**추가 파생 문제:** 그룹을 풀어도 알맹이인 `SearchPlaceResponseDto`는 `{placeId, placeImageUrl, categoryName, placeName, x, y}` 6개 필드뿐이다. 장소 선택/상세 카드가 쓰는 `address`(`:1693`), `time`(`:1582`,`:1700`), `description`(`:1578`,`:1716`), `tags`는 **응답에 존재하지 않는다.** 지금은 목데이터가 이 칸을 채워주고 있어 문제가 드러나지 않았을 뿐, 버그를 고치면 곧바로 빈 칸으로 노출된다.

### 2-3. 🔴 P0 — 프리뷰 실패 시 0값으로 플랜이 저장됨

`CourseCreationFlow.tsx:463` 부근:

```ts
requiredTime: serverPreview?.requiredTime ?? 0,
totalDistance: serverPreview?.totalDistance ?? 0,
travelTime: pv?.duration ?? 0,
stayTime: pv?.stayTime ?? 0,
```

프리뷰가 실패해도(`previewFailed === true`) 저장 CTA가 살아 있어 **소요시간 0분·거리 0m짜리 플랜이 서버에 영구 저장된다.** 명세상 이 필드들은 재계산 API가 따로 없어 사후 복구 경로도 없다.

### 2-4. 🟡 P1 — `transportTime` 부활

| | 260819 명세 `SurveyResultDto` | 로컬 백엔드 소스 | FE |
| --- | --- | --- | --- |
| emotion | string | ✅ | ✅ |
| startTime / endTime | string | ✅ | ✅ |
| transport | string | ✅ | ✅ |
| location | `{x, y}` | ✅ | ✅ |
| **transportTime** | **integer(int32)** | ❌ 없음 | ❌ 주석 처리 |

FE는 "서버 DTO에 없다"는 이유로 `TODO(transportTime)`을 달고 UI 질문 자체를 비활성화해 뒀다(`CourseCreationFlow.tsx:126`, `shared/types/index.ts:54`). **명세에 정수형으로 돌아왔으므로 복구 대상이다.**

단, FE의 기존 선택지는 문자열(`'30분 이내'`, `'1시간 이내'`, `'2시간 이내'`, `'상관없어요'`, `'직접입력'`)이고 명세는 정수다 → **분(minute) 단위 정수 변환 규약이 필요하며, `'상관없어요'`의 표현(0? 미전송? 큰 수?)은 BE 합의 사항이다.**

> ⚠️ 이 레포의 `backend/` 체크아웃은 마지막 커밋이 **2026-07-17**(`673646c`)로 명세보다 한 달 이상 낡았다. `transportTime`이 로컬 소스에 없는 것은 "BE 미구현"이 아니라 **로컬 사본이 낡은 것**일 가능성이 높다. 앞으로 로컬 `backend/`를 진실의 원천으로 삼지 말 것.

### 2-5. 🟡 P1 — `PlanDetailDto.departurePoint` 정식 포함

`plan.types.ts:44`는 이 필드를 `departurePoint?: DeparturePoint | null`로 두고 *"백엔드가 상세 응답에 추가 예정(배포 전엔 undefined일 수 있음)"* 주석을 달았다. **260819 명세에 정식 포함**되었으므로 주석을 갱신하고, 수정 플로우의 "출발지 없음" 방어 분기를 정리할 수 있다.

### 2-6. 🟢 P2 — 명세 자체의 품질 이슈 (BE 문의 목록)

1. `POST /api/place/recommend` — 응답 타입 미정의. `ResponseEntity<List<RecommendPlaceResponseDto>>`로 좁히거나 `@ApiResponse(content = @Content(array = ...))` 명시 요청. **§2-2 해결의 전제.**
2. `POST /api/plan/{planId}/images` — `images`가 **query 파라미터의 binary 배열**로 표기됨. 실제로는 multipart 본문일 것(FE도 그렇게 보내고 있음). `@RequestPart` 표기 필요.
3. `POST /api/plan-place/{planId}/preview` — `summary`/`description` 누락(태그만 있음).
4. **전 스키마에 `required` 배열이 없다.** 모든 필드가 optional로 읽혀 필수/선택 판단이 불가능하다. 최소한 생성 계열 DTO만이라도 `@Schema(requiredMode=REQUIRED)` 적용 요청.
5. `tripStartDate`/`tripEndDate`가 `date-time`인데 FE는 타임존 없는 `2026-08-19T09:00:00` 형식을 보낸다. 서버 파싱 규약(로컬 시각 취급 여부) 확인.
6. `emotion`이 자유 문자열이라 FE가 한국어 문장(`'그냥 기운이 없고 지쳤어요'`)을 그대로 보낸다. ans-014 매핑 테이블 도입 시 **코드값 전환 협의 필요**.
7. `PlanCopyRequestDto.scheduledDate`는 `date`(날짜만), 다른 곳은 `date-time`. FE `ClonePlanBody.scheduledDate`가 어떤 형식을 보내는지 확인 필요.

## 4. 결정이 필요한 것

1. **Phase 1-1을 지금 고칠 것인가, ans-014 §6(웰니스 공공데이터 도입)까지 기다릴 것인가.** ans-014는 어차피 추천 응답 계약을 다시 정한다고 예고했다. 다만 그 승인 시점이 불확실하고, 그동안 사용자는 계속 목데이터를 본다 → **먼저 고치는 쪽을 권한다.** flatten 로직은 계약이 바뀌어도 버려지는 코드가 아니다.
2. **1-3의 빈 필드 처리 방향** — 칸을 숨길 것인가(레이아웃 변동), 플레이스홀더를 둘 것인가(정보 없음 명시).
3. **2-3의 상세 보강 주체** — BE 필드 추가 vs FE N+1 조회.
