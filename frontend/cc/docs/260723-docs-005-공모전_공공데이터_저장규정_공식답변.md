1. **공공 데이터 식별자 서비스 DB 저장 가능 여부** — 공공 API 데이터의 자사 DB 저장이 금지된 것으로 아는데, 조회용 '식별자'만 DB에 저장하는 형태는 가능한지
2. **공공 데이터 사용 규정 상세 문서 위치** — 상세 사용 규정 문서를 어디서 열람할 수 있는지

## 사무국 답변 (원문 요지)

### 1. 식별자 DB 저장 — 가능

- 식별자만 저장하는 구조는 **정상적으로 가능하며 심사 대상에 포함**됨
- FAQ의 '로컬 DB 저장 방식 제한'은 한국관광공사 OpenAPI의 **원천 데이터(상세 텍스트, 이미지 등)를 자사 서버에 통째로 복사·저장하여 API 호출 없이 서빙하는 행위**를 의미
- 데이터 조회·매칭용 식별자(콘텐츠 ID 등)만 자사 DB에 저장하고, 실제 상세 데이터는 식별자 기반으로 **TourAPI를 실시간 호출**하여 화면에 구현하는 구조는 정상적인 활용 형태
- **단, 심사 기준상 서비스 개발 기간 내 OpenAPI 실제 호출 내역(로그)이 검증되어야 하므로, 실시간 호출 로그가 정상적으로 남도록 구현할 것**

### 2. 상세 사용 규정 문서 위치 — 사무국 소관 아님

- 한국관광공사 OpenAPI 자체의 상세 사용 규정·법적 가이드라인 문서 위치는 공모전 운영사무국 소관이 아님
- 한국관광콘텐츠랩 사이트의 '서비스 소개'/'OpenAPI' 메뉴에서 찾기 어려우면, **한국관광콘텐츠랩 자체 Q&A 게시판 또는 고객센터**로 문의하면 열람 위치를 안내받을 수 있음

## 프로젝트 적용 시사점

1. **plan-012 §5의 "식별자만 저장 + 표시 시 실시간 재조회" 아키텍처가 공식 확인됨** — 백엔드 `publicDataRef` 스키마 협의를 그대로 진행하면 됨
2. **실시간 호출 로그가 심사 요건** — BFF/백엔드의 공공 API 호출부에 호출 로그(시각, 엔드포인트, 응답 상태)를 남기는 로깅을 필수 구현 항목으로 승격. 과도한 캐싱으로 실호출이 사라지면 심사에서 불리할 수 있으므로, 캐시 TTL 설계 시 "개발 기간 내 실호출 내역이 충분히 남는 수준"을 함께 고려
3. **plan-012 미결 사항 #7(BFF 단기 캐시 허용 범위)** — 이 답변으로 "원문을 영구 복사해 API 호출 없이 서빙"하는 것만 금지임이 명확해져, 전송 최적화 목적의 단기 캐시는 허용 범위로 해석 가능. 다만 상세 규정 문서는 한국관광콘텐츠랩에 별도 확인 필요 (미결 유지)
