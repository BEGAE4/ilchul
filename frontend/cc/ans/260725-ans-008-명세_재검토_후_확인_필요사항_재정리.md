## A. 스웨거로 해소됨 — 질의 불필요, 바로 구현에 반영

| 항목 | 스웨거 확정 내용 | 반영처 |
| --- | --- | --- |
| 댓글 응답 wrapper | 전 reply 엔드포인트 raw 반환: GET → `ReplyListResponse`, POST 201 → `integer`, PATCH/DELETE/좋아요 200 → `integer`. `{status, data}` wrapper 없음 | **작업 1 즉시 착수 가능** — 실응답 샘플 대기 불필요 |
| 제재 등록 응답 | 200 + `{ sanctionId: int32, adminReportDetailResponseDto }` — 키 이름·타입·상태코드 모두 확정 | 작업 4-2: 매퍼에서 `String(sanctionId)` 변환 확정 |
| 제재 등록 요청 | required는 `type`/`resolution`뿐 (`message`는 minLength 1, `durationDays` optional). `reportId` 필드 없음 | 작업 4-2: body 4필드 전송 유지, reportId 제거 확정 |
| 신고 상태 PATCH | `status` enum 전체 4종(`PENDING\|REVIEWING\|RESOLVED\|REJECTED`) 스키마 확정 | 작업 4-1: 타입 확대 근거 확정 |
| 인기 목록 항목 `id` | 플랜/장소 모두 `int32` | 작업 5-4: `string` → `number` 교정 확정 |
| `/api/reports`(복수형) | 백엔드 경로에 **없음** (단수 `/api/report`만 존재) | 작업 4-3: BFF 라우트 삭제 확정 |
| 내 제재 목록 API | 48개 경로에 **없음** | MySanctions 처리는 팀 결정 사안으로 이동 (§C) |
| `imageIds` | query `int32[]` required | 작업 2-4: `paramsSerializer` 방식 그대로 |
| `PlanDetailDto` | 21개 필드에 `departurePoint` **없음** 재확정 | 작업 3 블로킹 상태 재확인 (§B-1) |
| (타 담당 참고) | mypage/plans 204 정의 있음 · `DELETE /api/recent` body `{name, createdAt}` · `POST /api/recent` 응답 200 | §2-6, §2-7 담당자에게 인계 |

## B. 여전히 백엔드 질의 필요 — 9건 → 실질 4건 + 세부 묶음 1건

> **주의**: 스웨거 `required` 배열은 75개 스키마 중 4개(신고·문의 요청 DTO)에만 정의됨. 나머지 스키마의 required 부재는 "optional 확정"이 아니라 **정보 없음**이다.

1. **[작업 3 블로킹] plan-place preview/update의 `departurePoint`** — 생략 시 저장된 출발지가 유지되는가, null로 덮어써지는가? `PlanDetailDto`에 departurePoint 추가 가능한가? (클라이언트에 기존 플랜 출발지를 얻을 소스가 전무함이 스웨거로 재확정됨)
2. **[작업 3 블로킹] 스탬프 `location` 파트 필수 여부** — 생략 시 400인가, 위치 검증 없이 승인인가?
3. **플랜 생성 검증 정책** — requiredTime 등 누락 시 400인가? 프리뷰 실패 시 0 기본값 허용? `totalDistance` 단위(스웨거 `int32`인 점은 m 방증 — km면 소수 필요) + 프리뷰 `duration` = 요청 `travelTime` 동일 의미·단위인가?
4. **`GET /api/sign/userinfo` 응답 스키마** — 스웨거는 빈 `object`. 숫자 `userId` 포함 여부 (본인 댓글 판별 userId 전환·신고 ownerId 정리의 선행 조건)
5. **세부 런타임 동작 (구현과 병행 확인 가능, 블로킹 아님)** — 최상위 댓글 `parentReplyId` 값(null/0/생략), `lastReplyId=0` 첫 페이지 해석, isDeleted 댓글 content 마스킹 여부, RESOLVED 직접 전이 비즈니스 규칙, clone `scheduledDate` 실제 필수 여부, 삭제용 이미지 `imageId` 노출 방법, 내 제재 목록 API 신설 계획

## C. 팀 내부 결정 사항 (백엔드 무관)

- **MySanctions 화면** — API 부재가 스웨거로 확정됐으므로: 백엔드 신설 요청 vs 화면 비활성 처리 중 택일
- **admin mock 폴백** — 완전 제거 vs env 기반 dev 게이트 유지
- **플랜 복제 `scheduledDate` UI** — 날짜 선택 모달 vs 기본값(오늘/tripStartDate)

## D. 환경 확인

- `NEXT_PUBLIC_API_BASE_URL` — 저장소에 `.env` 없음. 미설정 시 apiClient 직행 호출(댓글·신고·플랜)이 Next 서버로 가서 404 → 작업 1 수동 검증 불가. 백엔드(`localhost:3845`) 기동과 함께 착수 전 확인
