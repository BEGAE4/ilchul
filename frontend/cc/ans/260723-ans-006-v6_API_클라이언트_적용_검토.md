## 2. 수정 필요 — 런타임 오류 위험이 큰 불일치

### 2-1. 댓글 (v6-006) — 응답 DTO 구조가 전면 불일치
- **목록 응답**: 명세 `ReplyListResponse = { replies, hasNext }` vs 클라 `GetRepliesResponse = { status, data, hasNext }` (`comment.types.ts:24-28`). `useComments.ts:21`이 `res.data`를 읽음 → 스펙 백엔드에선 undefined.
- **작성 응답**: 명세는 raw `number` 반환 vs 클라는 `{ savedReplyId }` 기대 (`comment.types.ts:36-38`).
- **좋아요 응답**: 명세는 raw `number` vs 클라는 `{ status, data: { replyId, likeCount, isLiked } }` (`comment.types.ts:40-47`) — `useComments.ts:92`의 낙관적 업데이트가 깨짐.
- **멘션 필드명**: 명세 `mentions[].userNickname` vs 클라 `username` (`comment.types.ts:1-4`).
- 중첩 대댓글 타입도 다름(명세는 중첩 `ReplyListResponse`, 클라는 평면 배열). `replyCount`/`isDeleted` 누락.

### 2-2. 플랜 (v6-004) — swagger 교차 검증 완료
- **`userNickName` → `userNickname`** 오타 수준 필드명 불일치 (`plan.types.ts:44`). swagger 확인 결과 백엔드는 소문자 n — 바인딩 안 됨. **확정 버그**.
- **`planImages`는 명세에 없는 필드** — 명세는 `planImageUrls`만 존재 (`plan.types.ts:50,178`). **확정**.
- **플랜 생성 요청 누락 필드**: 명세 필수인 `requiredTime`, `totalDistance`, 장소별 `travelTime`/`stayTime`을 생성 플로우가 보내지 않음 (`CourseCreationFlow.tsx:278-299`, `plan.types.ts:61-71`).
- **이미지 삭제 `imageIds` 직렬화**: swagger는 query `int32[]`인데 클라는 `join(',')` 문자열 전송 (`plan.api.ts:117`) — `imageIds=1,2` 형태라 Spring 배열 바인딩 실패 위험. 배열 그대로 넘겨 axios 기본 직렬화 사용 권장.

### 2-3. 플랜 장소 (v6-005)
- **`departurePoint` 누락**: 명세상 `UpdatePlanPlaceRequestDto` 필수 필드인데 수정 미리보기/확정 호출이 `{ places }`만 전송 (`MyCourseDetailPage.tsx:290,305`, `plan.types.ts:101`).
- **스탬프 `location`**: JSON Blob 파트로 전송 (`plan.api.ts:92-94`) — Spring 관례상 아마 정상이나, 위치 정보가 null이면 파트 자체를 생략 (`MyCourseDetailPage.tsx:242-243`) → 위치 없는 스탬프 요청 가능. 백엔드 필수 여부 확인 필요.

### 2-4. 고객 문의 (v6-009) — 경로/enum이 명세와 다른 체계로 구현됨
- **경로 불일치**:
  - 내 문의 목록: 명세 `GET /api/cs-inquiry/my`인데 클라는 `GET /api/cs-inquiry`를 호출하고 BFF가 `size` 파라미터 유무로 구분 (`inquiry.api.ts:15,24`, `cs-inquiry/route.ts:16`).
  - 답변 작성: 명세 `POST /api/cs-inquiry/{id}/reply`인데 클라는 `POST /api/cs-inquiry/{id}` (`inquiry.api.ts:86`).
- **`InquiryStatus` enum 오류 (양쪽 feature 모두)**: 명세 `OPEN|IN_PROGRESS|RESOLVED|CLOSED` vs `inquiry.types.ts:1` `PENDING|ANSWERED`, `adminInquiry.ts:18` `OPEN|ANSWERED|CLOSED`.
- **필드명**: 수정 시 명세 `newImages` vs 클라 `images` (`inquiry.api.ts:69-70`); 명세에 없는 `categoryId` 추가 전송 (`inquiry.api.ts:51`); 목록 아이템이 `inquiryType` 대신 `categoryName` 사용 (`inquiry.types.ts:39-47`).
- **admin-inquiry feature 전체가 off-spec**: `/api/admin/inquiries/**` 표면(목록/상세/상태변경/답변 CRUD)은 v6에 없는 엔드포인트이며 mock 전용 (`adminInquiry.api.ts:16-72`, `admin/inquiries/route.ts:11`). 페이지네이션도 page/size 방식으로 명세(커서 `lastInquiryId`)와 다름. v6 체계(`GET /api/cs-inquiry`, `POST /api/cs-inquiry/{id}/reply`)로 이관 필요.

### 2-5. 신고 (v6-008)
- **PATCH 상태 변경 제한**: 클라·BFF mock이 `REVIEWING|REJECTED`만 허용 (`adminReport.api.ts:81`, `admin/reports/[reportId]/route.ts:57`) — 명세는 전체 `ReportStatus` 허용.
- **제재 등록은 mock 전용**: `sanctions/route.ts:6` `useMock=true`, 실제 백엔드 호출 경로 없음. 요청 body에 명세 외 `reportId` 포함, 응답 필드명 `report` vs 명세 `adminReportDetailResponseDto` (`adminReport.ts:59-62`).
- **off-spec 경로**: `POST /api/reports`(복수형) mock 라우트 잔존 (`src/app/api/reports/route.ts`, `report.api.ts:67`). `MySanctions` 관련 타입(`report/types/report.ts:127`)은 대응 엔드포인트가 명세에 없음.

### 2-6. 마이페이지 (v6-002)
- **`GET /api/mypage/plans` DTO 대폭 불일치**: 클라 `MyPlan`(`plan.types.ts:2-11`)이 `tripDate`/`placeCount`/`isPublic` 등 명세에 없는 필드 사용, 명세 필드 `tripStartDate`/`tripEndDate`/`requiredTime`/`isPlanVisible` 누락. 명세 `204`(플랜 없음) 미처리.
- **`PATCH /api/mypage/profile`**: 명세는 3필드 모두 optional인데 클라 타입은 전부 필수 (`profile.types.ts:7-11`).
- **공개 토글 304 시맨틱 상실**: 프록시가 `{status}` JSON으로 감싸 304 구분 불가 (`plan/visibility/[planId]/route.ts:33`).
- **스크랩 목록**: 날짜 필드 nullability만 명세와 다름 (`plan.types.ts:18-27`) — 경미.

### 2-7. 최근 검색어 (v6-007)
- `POST /api/recent`: 프록시가 201 반환(명세 200, `recent/route.ts:38,54`), 요청에 명세 외 `createdAt` 포함 (`search.api.ts:14-17`).
- `DELETE /api/recent`: §1 참조 (개별 삭제 미구현).

## 3. 횡단 이슈

1. **광범위한 mock 폴백**: userinfo/profile/summary/scrapped/plans/recent 등 BFF 라우트가 백엔드 미연결·에러 시 하드코딩 mock을 200으로 반환 → 실패가 성공처럼 보임. 특히 `userinfo`의 비401 에러→mock 반환은 `useAuth.ts:19-22`가 로그인 상태로 오판하는 위험 (`sign/userinfo/route.ts:28-38`).
2. **인기 장소/플랜 API 이중 구현**: `place.api.ts:30-51`(apiClient 직행)과 `main.api.ts:11-52` + BFF 프록시가 병존 — 단일화 권장.
3. **admin 계열(신고 제재, 문의 관리)이 mock 전용** — 실제 백엔드 연동 자체가 안 되어 있음.
