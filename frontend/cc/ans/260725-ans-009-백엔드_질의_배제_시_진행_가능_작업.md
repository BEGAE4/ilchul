# 백엔드 질의 4건 배제 시 진행 가능한 작업

> 대상 계획: [260725-plan-013](../plan/260725-plan-013-v6_api_alignment_yeonju_scope.md)
> 결론: **작업 3(플랜 장소)만 전면 대기, 나머지 작업 1·2·4·5는 전부 진행 가능** — 계획 분량의 약 90%.

---

## 즉시 진행 가능

### 작업 1 — 댓글 DTO 전면 수정 (전체 진행 가능)

raw 응답이 스웨거로 확정되어 대기 사유가 없음. 타입 재작성 → api → 훅 → UI(중첩 대댓글·isDeleted) 전부.
멘션 전송, 답글 더보기(1-5)도 가능.
**단 하나 보류**: 본인 댓글 판별의 userId 전환 — Q4(userinfo에 숫자 userId 포함 여부)에 종속. 현행 닉네임 비교를 유지한 채 나머지를 진행하면 됨(원래도 선택 항목).

### 작업 2 — 플랜 확정 버그 (사실상 전체 진행 가능)

- 2-1 `userNickName` rename, 2-2 `planImages` 삭제, 2-4 `imageIds` 직렬화, 2-5 주석 갱신·중복 함수 삭제: 전부 가능
- 2-3 생성 요청 필수 필드 보강: **주 경로(프리뷰 성공 → order 조인으로 채워 전송)는 진행 가능** — 필드를 채워 보내는 것 자체가 어떤 답변이 오든 명세에 더 가까움. Q3에 종속되는 건 두 조각뿐:
  - 프리뷰 실패 시 0 기본값 허용 여부 → 일단 0 기본값 + 주석으로 구현하고 답변 후 조정
  - `CourseCreationFlow.tsx:1315`의 km 표기 수정 → 단위 답변 대기 (한 줄짜리 수정이라 마지막에 반영)
- clone `scheduledDate` 전송(2-5): 스웨거 DTO에 존재하고 다른 호출부는 이미 전송 중 — 기본값 방식으로 진행 가능(날짜 UI 방식만 팀 결정)

### 작업 4 — 신고 admin 정합화 (전체 진행 가능)

- 4-1 PATCH 상태 타입 확대: enum 스키마 확정 — RESOLVED 전이 비즈니스 규칙은 세부 질의로 남지만, 타입·mock 확대는 명세 기준 진행
- 4-2 제재 등록 실연동: 응답 형식(200, `sanctionId: int32`, 키 이름)·요청 required 모두 스웨거 확정 — **이 작업의 핵심이며 대기 사유 없음**
- 4-3 `/api/reports` 삭제: 백엔드 부재 확정 — 폴백 분기·idempotency 유틸 정리까지 전부
- MySanctions만 팀 결정 대기(백엔드 질의와 무관) — 타입 유지 상태로 나머지 진행

### 작업 5 — 횡단 이슈 (전체 진행 가능)

- 5-1 userinfo mock 폴백 제거: Q4는 응답 **스키마 확장**(userId 전환용) 질문이지 폴백 제거와 무관 — `useAuth` catch가 이미 미로그인 처리하므로 진행 가능
- 5-2 mypage GET·recent 폴백 제거 + 204 처리: 진행 가능
- 5-3 admin 폴백 정리: dev 게이트 방식이면 즉시 진행 가능(완전 제거 여부만 팀 결정)
- 5-4 popular 단일화 + `id: number` 교정: dead code 삭제 + 스웨거 확정 — 진행 가능

## 대기

### 작업 3 — 플랜 장소 (전면 대기, Q1·Q2 블로킹)

- `departurePoint`: 클라이언트에 기존 플랜 출발지 데이터 소스가 전무해 백엔드 답변 없이는 수정 방식 자체를 정할 수 없음
- 스탬프 `location`: 필수 여부에 따라 차단 UI 추가 vs 현행 유지가 갈림
- 단, 3-3(생성 프리뷰 요청에 `planDescription` 전송 등)은 작업 2-3과 같은 파일이므로 그때 함께 처리
